# Addresses to cripple rather than drop.
#
# THE SPLIT WITH custom-ip-blocklist.txt: VPNs and tunnels come here and are
# shaped; app estates — imo, BIGO/Likee, TikTok Live, the live-streaming and
# random-chat backends, DNS-changers — are dropped there. The reasoning is in the
# paragraph below: a dropped app backend just fails, where a dropped VPN node tells
# the client to try the next one. That file's header carries the same rule.
#
# Everything here is capped at 100 kbit/s each way, instead of being blocked
# outright. The point is that a tunnel behaves like a bad connection rather than
# a filtered one: there is no clean failure for the client to detect and route
# around, and an app that reconnects instantly when a node is dropped has
# nothing to react to when the node merely becomes slow.
#
# THE CAP IS NOW THE WHOLE OF IT — changed 2026-08-13. This file used to add
# 400 ms of latency, 100 ms of jitter and 3% random loss on top, and the old
# text here argued the jitter mattered more than the bitrate. Watching it work
# says otherwise: the clients being shaped choose between candidate nodes by
# RTT and loss, so impairing a node made it trivially easy for them to spot,
# discard and go hunting for an unthrottled one. The impairment was advertising
# which nodes had been touched.
#
# A bare rate cap does not show up in that scoring. A latency probe is a couple
# of small packets and passes under the cap untouched, so the node keeps
# measuring healthy and keeps being selected, while anything carrying real
# traffic crawls. The client staying on a node that cannot move data is the
# whole objective; a node it can tell is bad is a node it will replace.
#
# The queue under the cap is fq_codel, not a plain fifo, and that is part of the
# same design — a deep fifo at 100 kbit/s is minutes of standing buffer, which
# an RTT probe reads exactly the way it used to read netem's delay. See the
# comment on the throttled class in qos.nix.
#
# Same format and same guarantees as custom-ip-blocklist.txt: parsed at build
# time, so a typo fails the rebuild rather than silently shaping nothing, and
# overlapping entries are collapsed. Add live with `tempthrottle add <ip>`,
# which is cleared by the next rebuild — anything worth keeping belongs here.
#
# TEST SITE: https://ash-speed.hetzner.com/ — Hetzner's Ashburn speed test.
# Present so the shaping can be verified end to end from a LAN client: run the
# speed test and the result should be ~100 kbit/s. Latency should now look
# ORDINARY — that is the point of the 2026-08-13 change, not a sign the shaping
# has stopped working, so judge it on throughput alone. A ping to this address
# staying fast while the transfer crawls is the shaper behaving correctly.
# Remove it once the throttle is confirmed working.

# --- 2026-09-01: a bare-IP-CN certificate, on two unrelated networks ---------
#
# Two TLS-on-443 proxy endpoints that share a certificate signature not
# previously recorded in this file. Both serve, for EVERY SNI offered
# (including www.wikipedia.org and github.com, names neither could front):
#
#   subject = CN=<an IP address that is not the host's own>
#   issuer  = C=US, O=Let's Encrypt, CN=E6
#   SAN     = DNS:<that same IP literal>
#
# THE CERTIFICATES ARE FORGED, and the SAN is what proves it rather than the
# absurd-validity test this file usually leans on — the dates here are an
# unremarkable 35 days. Let's Encrypt's IP-address profile issues an IP SAN and
# validates control of that address; an IP literal sitting in a DNS SAN is not
# a form LE emits. The named addresses settle it:
#
#   177.177.83.5     CN=215.179.170.230   AS749, US Department of Defense
#   85.189.100.216   CN=49.109.96.74      AS9605, NTT DOCOMO mobile, JP
#
# Neither operator issued a certificate to a proxy in ProWave or Kaopu space.
# The issuer string is pasted on; the chain does not verify, no intermediate is
# presented, and the CN is arbitrary because no client ever reaches these by
# name — it is camouflage to complete a handshake for someone who already has
# the address. Serials and validity windows differ between the two, so this is
# one toolchain deployed twice, NOT a pass-through to a shared upstream.
#
# Both: no PTR that means anything, tcp/22 open, DoH 404 with an empty body and
# 853 closed, so neither is a resolver and neither belongs in the blocklist.
#
# THE SIGNATURE IS WORTH SWEEPING FOR. "CN is an IP literal that is not this
# host, in a DNS SAN, issued by Let's Encrypt" is cheap to probe and hard to
