# a /16 or wider where a provider is not worth enumerating host by host for a
# device that has no business there. That is only defensible because it applies
# to the pool rather than the house.
#
# One CIDR per line, v4 or v6, # comments. Parsed at build time.
#
# PREFIXES THE ASN EXPANSION CANNOT SEE, added 2026-08-13.
#
# custom-lowtrust-asns.txt turns AS numbers into ranges by reading
# ip2asn-combined.tsv, and that table is a static 43 MB file checked into this
# repo with no refresh mechanism. It is already out of date: fifty-four
# addresses in custom-throttle-list.txt sit in prefixes the table calls "not
# routed" while live BGP names an origin AS that is on the list. The expansion
# faithfully skips them, because it cannot know what the table does not say.
#
# Every prefix below was confirmed against live BGP (Team Cymru) and RIPE/ARIN
# whois, and each belongs to a provider already named in the ASN file. They are
# listed here rather than fixed at the source because refreshing the table is a
# separate job with its own risk; when it is refreshed these become redundant
# and can be deleted, which is why they are grouped and dated rather than
# scattered.
#
# The announced prefix is used rather than the narrower inetnum — same basis the
# ASN expansion works on, and it is the origin AS that makes the range the
# provider's.

# file is for. This entry is a /32, deliberately, and the reason is scope rather
# than breadth: it needs to apply to the pool and not to the house, and this is
# the only pool-scoped destination list there is. custom-ip-blocklist.txt would
# have given the right narrowness with the wrong reach.
#
# 46.165.254.136 is AS28753, Leaseweb DE-FRA-10, TTL 56 on the wire. It is the

#

# to do, but 46.165.192.0/18 alone is 16k addresses and the whole of Leaseweb DE

# call was the /32 for now, knowingly: this holds one address and nothing more.
#
# So expect it to be outrun. A second Leaseweb address appearing for a pool

# --- SUBSCRIPTION SOURCE FOR PUBLIC PROXY NODE LISTS, 2026-08-29 -------------
#
# GitHub's raw and Pages edge. whois gives the range whole:
#   185.199.108.0 - 185.199.111.255, netname US-GITHUB-20170413, GitHub, Inc.
# One /22 covers every current raw.githubusercontent.com A record and the four
# addresses GitHub publishes for Pages, so there is nothing to keep in sync.
#
# WHY A CONTENT HOST IS IN A FILE OTHERWISE FULL OF HOSTING PROVIDERS. Public
# "free config" repositories publish thousands of vless/vmess/trojan endpoints
# as a plain text subscription and refresh them every few minutes. A client
# pointed at one never resolves any endpoint by name — it reads an address out
# of the file and dials it — which is why the node itself is invisible to every
# DNS instrument here, and why blocking nodes one at a time cannot win against
# a list that replaces them faster than they can be added.
#
# The subscription fetch is the part that does not rotate. Cutting it leaves a
# client with only whatever it had already cached.
#
# COLLATERAL, ACCEPTED KNOWINGLY: this is also every *.github.io site and every
# other raw.githubusercontent.com fetch, for pool devices. That is the price of
# using the announced range instead of chasing four host addresses that GitHub
# is free to renumber.
#
# WHAT IT DOES NOT COVER, DELIBERATELY. cdn.jsdelivr.net serves the same repos
# byte-for-byte through its /gh/ path, so a client that switches mirrors walks
# straight past this. jsDelivr was declined because it is a general-purpose CDN
# carrying script and font assets for a large part of the ordinary web, and the
# breakage would not look like a blocklist problem to whoever hit it. If a pool
# device is later seen refreshing a node list over jsDelivr, that is this entry
# being outrun rather than a new finding — and the trade is worth re-opening
# then, not pre-emptively.
#
# Blocking here rather than by name because a DNS rule does not reach this
# class of client: the pool exists for devices that resolve nothing and dial
# addresses directly, and DoH would carry a name-based block away in any case.
#
# IPv4 only on purpose. lowtrust_policy already rejects all v6 LAN->WAN for
# pool devices, so a v6 prefix here would be unreachable — the same reason the
# rest of this file is v4.
185.199.108.0/22

# --- TWO TUNNEL SERVERS, 2026-08-29, both /32 --------------------------------
#
# Same standing as the 46.165.254.136/32 entry above and for the same reason:
# these need to reach the pool and not the house, and this is still the only
# pool-scoped destination list there is. Both were found in one whole-LAN
# capture on bingo. Neither was ever returned as an answer to any name in that
# day's blocky log, so both are dialled from hardcoded config and no DNS rule
# can reach either.

# 16.217.239.244 — the more sophisticated of the two, and the one worth reading
# the note on.
#
# It carried 100% of one pool device's bytes for the whole capture window. That
# device made essentially no other connections at all: no ordinary web traffic,
# no app backends, nothing but this and a little local multicast. A full
# tunnel, not a split one.
#
# WHAT MAKES IT NOTABLE IS THE CAMOUFLAGE. Every TLS handshake to it — over a
# thousand in the window — carried SNI `yahoo.com`, and probing the address
# directly returns a real, currently-valid DigiCert certificate for yahoo.com
# whose serial is byte-for-byte identical to the one genuine yahoo.com serves.
# The address is not Yahoo: yahoo.com resolves into Yahoo's own space, and this
# is 16.216.0.0/15, legacy HPE range now leased out through IPXO and delegated
# to netname NETUTILS.
#
# An address serving another site's genuine live certificate is XTLS-REALITY,
# which forwards any unrecognised handshake to the real target site so that
# scanners and active probes see a valid chain. That is what defeats the
# certificate test in the detecting-client-tunnels method — the cert is real,
# it is simply not this server's. The tells that survive are the ones used
# here: the address does not belong to the named org, and nothing ever resolved
# to it.
#
# THE WIDER RANGE WAS CONSIDERED AND DECLINED. 16.216.0.0/15 is IPXO lease
# space with many unrelated tenants in it, so it is shared infrastructure in
# the same sense as the AS132203 note in custom-imo-list.txt — the /32 is what
# the capture proved and the /15 would take strangers with it. Expect the
# server to move; a second IPXO or NETUTILS address for a pool device after
# this date is this entry being outrun, not a new finding.
16.217.239.244/32

#
# 87% of one pool device's bytes, TCP and UDP on port 8388 simultaneously. See

108.181.121.228/32

# --- A THIRD SERVER FOUND IN THE SAME CAPTURE AND DELIBERATELY NOT ADDED -----
#
# A pool device held one single TCP connection to 162.159.130.11:443 for the
# entire window, carrying 99.7% of its bytes — and near-symmetrically, roughly
# as much up as down. That ratio is the finding: bulk consumption runs perhaps
# fifty to one inbound, so a 1:1 stream of that size is a relay, not a download
# or a video. No SNI (the handshake predated the capture), no plaintext, and no
# resolver answer for the address that day.
#
# The reading is a proxy fronted by a CDN — a VLESS/VMess/Trojan endpoint
# reached through Cloudflare, which is a well-documented arrangement precisely
# because of what it does to blocklists.
#
# IT IS NOT LISTED BECAUSE 162.159.130.11 IS CLOUDFLARE ANYCAST. The address is
# shared by an enormous number of unrelated sites, so a /32 here would be
# indiscriminate collateral of a kind nothing else in this file comes close to,
# and it would not even be durable — the fronted endpoint is selected by SNI
# and Host header, not by address, so the same tunnel reappears on any other
# Cloudflare address without the operator changing anything.
#
# Recorded rather than dropped silently so that a later reader does not
# rediscover this flow and assume it was missed. Closing it needs a different
# instrument than a destination list — the CDN-fronting problem is the same one
# the GitHub raw entry above solves at the subscription layer, and the useful
# next step is finding what hands this client its endpoint, not blocking the
# edge it arrives on.
