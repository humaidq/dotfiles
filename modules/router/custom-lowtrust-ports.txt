# Ports dropped LAN->WAN for devices in the low-trust pool only. The global
# custom-port-blocklist.txt is unchanged and applies to everybody; this file is
# the stricter set that only pool devices get.
#
# Same format and guarantees as that file: parsed at build time, so a typo
# fails the rebuild rather than silently blocking nothing.
#
# Seeded from the 2026-08-13 captures, which showed one client using each of
# these as a transport with nothing resembling the port's real protocol on it.
# 22 is deliberately NOT in the global file: SSH from other devices on this LAN
# is legitimate, and that is exactly the distinction this pool exists to draw.
21
22
553
554

# 179, added 2026-08-13, and on different grounds from the four above: it was
# NOT seen in a capture. 179 is BGP, which two routers speak to exchange
# routes — nothing a phone, laptop or appliance on a home LAN has any reason to
# open, so the collateral is as close to nil as a port gets. Tunnel clients pick
# exactly that kind of port precisely because it is usually left open.
#
# Pool-only rather than global for the same reason 22 is: this router speaks BGP
# to nothing today, but a global rule would be a trap for whoever later runs a
# mesh daemon or a route server on this LAN, and it would fail with no useful
# error. Move it to custom-port-blocklist.txt if that is ever ruled out.
#
# Recorded as inference, not observation: if a capture ever shows a pool device
# actually using 179, say so here — it changes this from a cheap precaution into
# a confirmed transport.
179

# --- Six added 2026-08-14 on request ---------------------------------------
#
# NONE OF THE SIX APPEARS IN ANY CAPTURE. Every pcap from 2026-08-12 to 14 was
# checked for them, LAN->WAN, TCP and UDP: zero packets. These go in on the
# same basis as 179 above — inference from what the port is for, not
# observation of a pool device using it. If a capture ever shows one carrying,
# say so here; it changes the entry's standing.

# The four classic VPN transports. A pool device has no business establishing a
# VPN by any means, and these are what the off-the-shelf clients use when they
# are not bothering to hide.
1194    # OpenVPN, udp and tcp
51820   # WireGuard, udp
1723    # PPTP control channel — the GRE data path (proto 47) is untouched by a
        # port rule, but PPTP cannot start without this, so it is enough
#
# 1701 is L2TP, and custom-port-blocklist.txt DELIBERATELY LEFT IT OUT with a
# reason worth repeating rather than silently contradicting: "it rides inside
# ESP and never appears on the wire on its own, so it would block nothing 500
# and 4500 do not already cover." That is correct for L2TP/IPsec, which is
# essentially all of it. It is added here anyway because bare unencrypted L2TP
# does exist and costs nothing to close for a pool device — but expect it to
# never fire. It is not a second layer on the IPsec block; it is the small
# remainder that block does not reach.
1701

# 1443 and 8008, neither of which is a VPN port.
#
# 1443 IS THE INTERESTING ONE. The global file already drops 943, 1943, 2943
# and 9443 as imo's tunnel transport family, and the shape of that family is a
# digit stuck on the front of 443. 1443 is the one member of the obvious series
# that was never listed. That is a pattern argument and not evidence — no
# capture shows 1443 in use — but it is the kind of gap a client walks into
# when the neighbours are closed.
1443
#
# 8008 is HTTP-alt, and the reason it is safe here is the rule's direction
# rather than the port being unused: lowtrust_policy matches
# `iifname lan0 oifname ppp`, so this is LAN->WAN only. Chromecast and Google
# Cast use 8008/8009 on the LAN, that traffic never reaches this chain, and
# casting keeps working for pool devices. A pool device reaching 8008 on the
# WAN is a different thing entirely.
8008

# --- 10505, added 2026-08-28 on request -------------------------------------
#
# NOT SEEN IN ANY CAPTURE IN THIS REPO, and nothing here records what was on it.
# Added on the operator's say-so, so it stands on the same footing as 179 and
# the 2026-08-14 six above: a port closed for the pool on the strength of what
# the port is, not on a pcap showing a pool device carrying over it. If a
# capture ever does, say so here — it changes the entry from a precaution into
# a confirmed transport.
#
# 10505 is unassigned by IANA and sits in the ephemeral range, which cuts both
# ways. It is the shape of port a tunnel picks precisely because nothing else
# wants it, and no ordinary service listens there, so the collateral for a pool
# device is as near nil as the entries above. But the same range is where a
# client's own source ports come from — harmless here only because this set is
# matched on `th dport` LAN->WAN, never on source port, so a pool device that
# happens to draw 10505 as its local port is untouched.
10505

# --- 60000, added 2026-08-28 ------------------------------------------------
#
# THE FIRST ENTRY IN THIS FILE SINCE THE ORIGINAL FOUR THAT A CAPTURE ACTUALLY
# SHOWS IN USE, which is worth stating plainly against the run of "inference,
# not observation" notes above.
#
# 192.168.50.221-20260828-1112.pcap, 20 seconds off bingo: MAC 9e:23:66:14:23:ba
# (galaxy a12, in the pool since 2026-08-13) talking to 46.165.254.136:60000 on
# UDP and TCP at the same time, 41 kB down and 25 kB up. Opaque from byte 0
# after a plaintext handshake of thirteen 2-byte `62 63` probes each way at
# ~10 ms spacing; the same magic appears length-prefixed on the TCP side as
# `0200 6263`. 1410-byte MTU-filling packets in both directions, so bulk
# transfer rather than codec frames. One DNS query in the whole window
# (www.google.com, a connectivity check) and no SNI anywhere — resolution had
# moved inside the tunnel, which is what rules out the P2P-call reading.
#
# THE PORT ALONE IS NOT THE FIX and should not be recorded as one. The /32 is in
# custom-lowtrust-subnets.txt and that is the entry doing the work; a tunnel that
# chose 60000 will choose something else. This is here because a port a capture
# caught carrying is worth closing whatever else is done about it.
#
# Collateral is nil for the same reason as 10505: unassigned by IANA, matched on
# `th dport` LAN->WAN only, so a pool device drawing 60000 as its own source
# port is untouched.
60000

# --- 8388, added 2026-08-29 -------------------------------------------------
#
# SEEN IN A CAPTURE, like 60000 above and unlike most of this file. A whole-LAN
# capture on bingo caught a pool device sending 87% of its bytes to a single
# address on 8388, TCP and UDP on the same port at once. That pairing is the
# identifying detail rather than the number: 8388 is the Shadowsocks default,
# and Shadowsocks is the one common transport that runs its UDP relay on the
# same port as its TCP stream. The address was never returned as an answer to
# any name in the day's resolver log, so it is dialled from config.
#
# Traffic was strongly outbound — several times more up than down — which is
# worth recording because it is the opposite of what a proxy used for browsing
# looks like, and it is the shape that would justify a closer look if this
# entry is ever reviewed.
#
# Collateral is nil on the same footing as 10505 and 60000: unassigned by IANA,
# matched on `th dport` LAN->WAN only, so a pool device drawing 8388 as its own
# source port is untouched.
#
# EXPECT THIS TO BE OUTRUN, AND FASTER THAN THE IMO PORTS. custom-port-
# blocklist.txt can argue its four ports are durable because eight apk-sim.sh
# runs never moved them — that app has the port compiled in. Shadowsocks does
# not: the port is one line of server config, and 443 is the conventional place
# to move it to, where no port rule can follow. The /32 in
# custom-lowtrust-subnets.txt is the entry doing the real work here, exactly as
# the 60000 note says of its own. This is worth closing anyway because a port a
# capture caught carrying is cheap to close, not because it will hold.
8388
