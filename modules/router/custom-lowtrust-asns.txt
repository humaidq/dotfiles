# Whole hosting networks dropped LAN->WAN for devices in the low-trust pool
# ONLY. Nothing here affects any other device on this LAN.
#
# One AS number per line, `#` comments. Expanded to CIDRs at build time from
# ip2asn-combined.tsv, so the ranges refresh whenever that table is updated
# rather than rotting the way a pasted list of prefixes would. An AS number that
# the table does not know fails the build rather than silently contributing
# nothing.
#
# WHY THIS EXISTS. Chasing individual nodes was losing: the tunnel client holds
# a pool of candidates, probes them, selects one, and refreshes the pool from a
# control channel fronted behind a CDN that cannot be blocked. Over a thousand
# addresses have been collected one at a time and the supply has not thinned.
# A pool device has no business reaching a rented VPS at all, so the whole
# market is a better unit than the individual host.
#
# WHY IT IS SAFE ENOUGH TO BE WORTH IT: the tunnel rents cheap VPSes, and
# mainstream app backends do not live there. AWS, GCP and Azure are absent from
# this list entirely, as are every CDN, so a pool device keeps WhatsApp, Botim,
# Apple, Google, Meta and ordinary browsing. What it loses is the small tail of
# services self-hosted on budget providers — real, occasional, and the accepted
# price. The generator refuses to build if any range here would swallow one of
# the addresses this network depends on; see the guard list in ip-blocklist.nix.
#
# Counted against the throttle list when chosen: these fifteen cover 88% of
# every node collected to date. Recompute rather than trusting that number —
# see the sweep in the throttle file's own notes for why counts here rot.

# --- Cogent, added on request after being argued against -------------------
#
# AS174 is TIER-1 TRANSIT, not a hosting company, and it is by a distance the
# widest entry in this file: 8,991 prefixes and 24 million addresses — more than
# every other AS here put together, and 0.56% of the routed IPv4 internet.
#
# The objection, recorded because it was raised and overruled rather than
# missed: a transit AS announces space on behalf of its customers, so this drops
# traffic to networks that have nothing to do with the twenty-five nodes that
# put it here. There is no way to tell from the announcement which of those
# 24 million addresses is a tunnel node and which is somebody's mail server.
#
# The counter-argument, which is what carries it: this is pool-only. The
# devices it applies to have already been judged not to need the open internet,
# and no other device on this LAN is affected by a single rule in this file.
#
# If a pool device starts failing to reach something ordinary and no other entry
# explains it, THIS IS THE FIRST ENTRY TO REMOVE. It is also the one most likely
# to be the cause, simply by size.
174     # Cogent — 25 collected nodes, 24M addresses of collateral
#
# STILL NOT COVERED, and not coverable this way — recorded so the gap is known
# rather than rediscovered:
#
#   ~25 singletons on residential and mobile carriers — Myanmar, Iran, Mexico,
#   Vietnam, Switzerland. These are the residential-exit pool, and an ASN list
#   of hosting providers can never catch them; that is what the per-address
#   rows in custom-throttle-list.txt are for.

# --- Zenlayer, added 2026-08-14, reversing the decline recorded below -------
#
# This entry was refused above the line for a while on two grounds. One of them
# turned out to be wrong and the other is still not satisfied, so the reversal
# is written out in full rather than just deleting the old note.
#
# WHAT THE DECLINE SAID: "an edge/CDN provider rather than a VPS shop, and 929
# prefixes of edge capacity is the kind of range that breaks something a phone
# actually needs. Ten nodes is not worth that. Revisit only with evidence of it
# carrying a tunnel."
#
# THE SIZE CLAIM WAS WRONG, and by enough to change the answer. Counted from
# the shipped ip2asn table: AS21859 announces 571 IPv4 ranges totalling 656,640
# addresses, which collapse to 775 CIDRs — 0.015% of routed IPv4. AS174 Cogent,
# already in this file and argued through at length above, is 24,004,735
# addresses. Zenlayer is THIRTY-SIX TIMES SMALLER than the widest entry already
# accepted here. "929 prefixes of edge capacity" was the number that carried
# the decline and it does not survive being computed.
#
# THE CARRYING EVIDENCE IS STILL ABSENT, and this is the honest gap. Across
# every capture taken 2026-08-12 to 14 there is not one established session to
# a Zenlayer address: no TLS, no SNI, no payload, 756 bytes inbound in total.
# The literal condition the decline set has NOT been met.
#
# WHAT REPLACED IT is a different and better argument, from 192.168.50.250's
# capture of 2026-08-13. The client ICMP-pings a spread of Zenlayer addresses
# and they REPLY — 98.98.207.98, .99, .102, .103, .105, 128.14.65.31, .34, .97,
# .150, 128.14.66.38, all alive, TTL 45-56. It then selects 98.98.207.106 and
# fires 1341 SYNs at tcp/443, which get nothing back. That is the same
# ping-then-probe-then-select cycle this file was written about, and it is
# running over CONTIGUOUS space: seven addresses inside 98.98.207.97-.106 and
# four inside 128.14.65-66. A client working consecutive addresses in one
# provider's block is the exact case where per-/32 rows lose and the AS is the
# right unit. Thirteen Zenlayer /32s are in the throttle list and nine more
# appear in that capture alone without ever having been added.
#
# So: not "it carried a tunnel", but "it is being enumerated as a pool, and the
# collateral is a fortieth of what the decline assumed". Pool-only, like
# everything here. The never-cover tripwire was dry-run against these 775 CIDRs
# before the entry went in and matches nothing.
#
# IF A POOL DEVICE LOSES SOMETHING and Cogent above is not the cause, this is
# the second entry to try removing — it is the only one in the file admitted
# without direct evidence of carrying traffic.
21859   # Zenlayer — 13 collected nodes, 656k addresses, enumerated as a pool
