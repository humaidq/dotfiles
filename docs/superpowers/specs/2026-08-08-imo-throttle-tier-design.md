# imo throttle tier

Date: 2026-08-08

## Problem

imo's estate is currently blocked outright in `custom-ip-blocklist.txt` — every
prefix announced by AS36131, an Alibaba /18, Tencent /32s, and the `*.imo.im`
origins, accumulated over eleven documented runs. Each run followed the same
shape: a layer was blocked, the app failed hard, and the operator re-homed onto
fresh infrastructure, which had to be found and blocked in turn.

That is the same failure the tunnel throttle list already documents for VPN
nodes: a dropped endpoint is replaced within a minute, a slow one is not,
because nothing fails cleanly enough to trigger failover.

## Goal

Move imo from a hard block to a second throttle tier: rate-capped at all times,
with heavy packet loss during the hours the household actually places calls and
light loss otherwise.

## Configuration

A new option block `sifr.router.imoThrottle`, parallel to the existing
`sifr.router.throttle`:

| Option | Default | Meaning |
|---|---|---|
| `rate` | `2mbit` | Rate cap, each direction, at all hours |
| `baseLoss` | `3%` | Loss outside the peak windows |
| `peakLoss` | `70%` | Loss inside them |
| `peakWindows` | `[ "07:00-11:30" "15:30-21:30" ]` | Local time |

Both routers are `Asia/Dubai` and systemd `OnCalendar` uses local time, so the
windows need no offset arithmetic.

## Data path

A new list file `modules/router/custom-imo-list.txt` feeds new nftables sets
`imo4`/`imo6`, generated by the same Python generator that `throttleList`
already reuses verbatim. The file format — CIDRs plus free comments — is
unchanged from the existing lists.

In `forward_throttle`, the imo rules mark `0x3` and are placed **after** the
existing `0x2` rules, so that an address appearing in both lists resolves to
the imo tier rather than the tunnel tier.

In `qos.nix`, a third HTB class `1:30` at `rate 2mbit ceil 2mbit`, with a netem
qdisc `handle 30:` carrying `loss` and `limit 1000` only. No added delay or
jitter: the requirement is a rate cap and loss, and netem's delay is what the
tunnel tier uses to break long-lived sessions, which is not the goal here. A
`handle 0x3 fw flowid 1:30` filter steers marked traffic in.

`1:30` is a single shared class. 2mbit is therefore the ceiling for all imo
traffic across the site at once, not per device. The existing tunnel class
behaves the same way.

## Scheduler

A `imo-throttle-schedule` service and timer. The service computes
minutes-since-midnight, tests it against `peakWindows`, and applies the
resulting loss with `tc qdisc change ... handle 30: netem loss N% limit 1000`
on both the ppp device (upload) and the LAN device (download).

`tc qdisc change` replaces the entire netem parameter set, so the service
re-specifies `limit` on every invocation rather than changing loss alone.

The timer fires `OnCalendar=*:00,30`, which is the granularity the 11:30 /
15:30 / 21:30 boundaries require. The service is additionally ordered `after`
and `wantedBy` `cake-sqm`: a pppd flap tears down and rebuilds the qdiscs, and
without that hook the class would return at base loss and stay wrong until the
next tick. With it, the timer is a self-healing backstop rather than the only
mechanism.

## Migration

All imo entries move from `custom-ip-blocklist.txt` to the new file, carrying
their comments with them. Those comments are the record of why each address is
known and must not be orphaned.

**This step is reviewed per block, not scripted.** A comment-keyword pass tags
293 of the 689 addresses as imo, but the tagging is unreliable in both
directions: several BIGO and TikTok blocks reference imo comparatively (for
example "the same overwall fallback widening that imo showed"), and a regex
migration would silently unblock them. Each candidate block is confirmed
against its own comment before moving.

## Consequences

Two effects follow from moving the whole estate, and both are intended:

- **imo works during base-loss hours.** At 2mbit and 3% loss, voice calls
  connect and hold. Roughly 13.5 hours of the day are base-loss, including all
  night and the 11:30–15:30 window.
- **70% loss is functionally a block.** TCP largely cannot complete a handshake
  at that rate, so the peak windows may still produce the re-homing behaviour
  the eleven runs documented. The throttle-beats-block argument applies at 3%,
  not at 70%.

Collateral falls rather than rises: a throttled /18 is slow-but-alive where a
blocked /18 was dead.

## Verification

- `nft list set inet router-blocklists imo4` shows the migrated addresses.
- `tc -s class show dev <lan>` shows class `1:30` with traffic counted.
- `tc qdisc show dev <lan>` shows netem `30:` at the loss matching the current
  hour.
- Forcing the service at a boundary flips the loss value on both devices.
- `nix flake check` passes.
